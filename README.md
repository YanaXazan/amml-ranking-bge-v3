# AMML Ranking Competition 2026 · BGE v3

Финальное решение основано на дообучении cross-encoder BGE для ранжирования русскоязычных фрагментов по релевантности запросу. Выбранная конфигурация достигла **0,943517 NDCG@10** на отложенной валидации. После переноса рецепта на полный обучающий набор был сформирован файл с 13 507 оценками. Зафиксированный результат на публичной части Kaggle — **0,936347**.

[Соревнование на Kaggle](https://www.kaggle.com/competitions/amml-ranking-competition-2026)

## Данные и разбиение

Строка `train.csv` или `test.csv` соответствует паре «запрос — фрагмент». Поля `query`, `title` и `text` содержат тексты, `id` связывает строку с отправкой, `query_id` задаёт список кандидатов, а `article_id` и `document_id` идентифицируют статью и фрагмент. Поля позиции, длины и источника описывают происхождение фрагмента. В train есть бинарная метка `relevance`. В `sample_submission.csv` задан порядок строк для двух столбцов `id,prediction`.

В 94% запросов по 10–11 кандидатов. В train 8 168 релевантных пар из 31 530 (25,9%). У каждого обучающего запроса есть кандидаты обоих классов, у 1 985 запросов — несколько релевантных фрагментов. Поэтому качество оценивается по порядку всей выдачи.

| Выборка | Пары | Запросы |
|---|---:|---:|
| Обучение при выборе checkpoint | 25 269 | 2 433 |
| Валидация при выборе checkpoint | 6 261 | 609 |
| Финальное обучение | 31 530 | 3 042 |
| Конкурсный тест | 13 507 | 1 305 |

Для выбора checkpoint использован один фиксированный GroupShuffleSplit с долей валидации 20% и seed 42. Группа определяется нормализованным текстом запроса с приведением регистра, ё к е и удалением конечной пунктуации. Проверка на исходных CSV подтвердила отсутствие общих query_id и нормализованных запросов между обучающей и валидационной частями. Между полными train и test также нет общих document_id. Между обучающей и валидационной частями общими оказались 1 083 фрагмента и 1 058 статей. Между полными train и test общими оказались 777 статей. Повторение фрагментов важно учитывать при интерпретации локальной оценки, поскольку разбиение сделано по запросам. Словари заголовков и IDF обучались на fit для валидации и на полном train для финальной модели. Дообучение использует только конкурсную разметку.

Локальная метрика сортирует кандидатов по убыванию оценки, при равенстве логитов использует строковый id по возрастанию. Для каждого запроса DCG по первым десяти позициям делится на DCG идеальной перестановки. Вес позиции с номером r, начиная с единицы, равен 1/log₂(r+1). При нулевом идеальном DCG результат запроса равен нулю. Общий результат представляет собой среднее с одинаковым весом каждого запроса. Проверочный SHA256 списка отсортированных validation id с разделителем перевода строки равен `83e2e8b4f2dcfe4a5249c717f6cadc2af467fddaa3d8c7eb2fdaed75ce8d58a8`.

## Анализ данных и подготовка текста

Исходная модель — `BAAI/bge-reranker-v2-m3`, ревизия `953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`. Cross-encoder на базе XLM-RoBERTa обрабатывает запрос и кандидат совместно, выдавая один логит. Финальный score для сортировки берётся до сигмоиды. В исходном запуске дообучались все 567 755 777 параметров.

В исходных CSV отсутствовали 1 382 заголовка в train и 691 в test. С учётом заглушек в финальной обработке эти числа выросли до 1 569 и 783. Пропуски в текстах запросов и фрагментов не обнаружены. Медиана длины фрагмента — 662 символа в train и 661 в test, максимумы — 8 808 и 10 622. В текстах встречались неразрывные пробелы, переносы строк, HTML-сущности, отдельные теги и ошибки декодирования. В числовых метаданных были пропуски, отрицательные значения числа фрагментов и разные форматы записи длины статьи. Эти поля использовались в ранних табличных моделях. Во вход BGE передаются запрос, заголовок и фрагмент, а идентификаторы помогают восстановить заголовки и сформировать пары.

Очистка восстанавливает обратимые ошибки кодировки, нормализует Unicode и пробелы, раскрывает HTML-сущности и удаляет распознаваемые теги и служебные символы. У заголовков удаляется суффикс «Википедия». Пропущенный заголовок восстанавливается по статье при согласии минимум двух разных обучающих документов. Пустой заголовок допустим. Регистр и буква ё сохраняются во входе модели.

Токенизатор собирает стандартную пару XLM-R из запроса и заголовка с текстом. Максимальная длина составляет 512 токенов, лимиты запроса и заголовка — 128 и 96. Для длинного фрагмента выбирается окно с максимальным IDF-взвешенным пересечением со словами запроса. При равенстве выбирается самое раннее окно. В полном train усечено 825 фрагментов, в test — 360. Для 34 тестовых фрагментов выбрано окно со смещением.

Логистическая регрессия служила ориентиром по лексическому сходству. Она получала признаки словесного и символьного TF-IDF, пересечения слов и чисел, а также метаданные. CatBoost использовал тот же тип признаков и учитывал их нелинейные сочетания. Qwen проверял семантическое сопоставление запроса и кандидата. В финальной BGE v3 предобученную модель адаптировали в две стадии. Число шагов парной стадии выбрали на валидации. Public и Validation измерены на разных выборках. Прочерк означает отсутствие зафиксированного результата.

Продление парной стадии проверялось до 600 шагов. Максимум пришёлся на шаг 400. Относительно шага 200 оценка выросла у 18 запросов и уменьшилась у 8. Описательный 95%-й bootstrap-интервал разности средних по запросам составляет от −0,000204 до +0,001215. Выбор на той же валидации ограничивает интерпретацию небольшого прироста. Эта конфигурация выбрана по результату на отложенных запросах и перенесена на полный обучающий набор для финального решения.

## Финальное обучение

Число обновлений и параметры расписания масштабированы по отношению размера полного train к fit. Обе стадии используют seed 42 и детерминированный режим. FP32-параметры оптимизируются AdamW с `foreach=False`, weight decay 0,01 и ограничением нормы градиента 1,0. Используются FP16 autocast, градиентный checkpointing и начальный AMP scale 1024. Каждая стадия заканчивается при достижении заданного числа успешных обновлений.

| Параметр | BCE | BCE + pairwise |
|---|---:|---:|
| Успешные шаги | 873 | 499 |
| Learning rate | 0,000005 | 0,000001 |
| Warmup, шагов | 197 | 25 |
| Полный горизонт линейного расписания | 3 943 | 749 |
| Накопление градиента | 8 | 4 |
| Микропакет на GPU | 1 документ | 1 пара |

После BCE модель оценивает обучающие документы. Для каждого положительного примера выбирается самый высоко оценённый отрицательный из той же статьи в том же запросе, при его отсутствии — самый высоко оценённый отрицательный из выдачи. При наличии второго отрицательного добавляется случайный. Веса зависят от абсолютного изменения NDCG@10 при обмене позициями и числа положительных кандидатов запроса. Вторая стадия добавляет к BCE взвешенный softplus от разности отрицательного и положительного логитов с коэффициентом 0,2.

## Запуск

1. Импортируйте `solution.ipynb` в Kaggle, подключите исходные `train.csv`, `test.csv` и `sample_submission.csv`, выберите Tesla T4 ×2 и включите Internet для загрузки базовой модели и пакетов. Ноутбук ищет подходящий каталог под `/kaggle/input` по именам и SHA-256. Каталог также можно задать в `DATA_DIR`.
2. Выполните **Run All**. Режим по умолчанию `MODE = "train"` запускает обе стадии дообучения и инференс. Ячейки с `%%writefile` создают временные модули для раздельных процессов двух GPU. Ноутбук проверяет версии GPU-стека до запуска обучения.
3. Возьмите `submission.csv` из напечатанной директории `/kaggle/working/bge3_run_…/`. Он содержит `id,prediction` в порядке официального шаблона. Для повторного инференса укажите `MODE = "predict"` и путь `SAVED_MODEL_DIR` к полной сохранённой папке `pair_stage/model/`.
4. Для запуска вне Kaggle используйте Linux x86_64, Python 3.13, Jupyter, две Tesla T4 и драйвер с поддержкой CUDA 13. Установите зависимости в окружение ядра командой `python -m pip install -r requirements.txt`. В первой ячейке задайте `DATA_DIR` и доступный для записи `OUTPUT_ROOT`.
